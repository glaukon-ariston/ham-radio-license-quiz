## Two new defects found and fixed — the meta-claim trap, on both sides

The brief's warning was specific: be suspicious of claims about the source's own error
patterns. Found two, in opposite directions:

1. **`bk-pra-3-35`** claimed the *printed exam text* reads "regiji LARU-a" as a
   "tiskarska/OCR greška" for IARU. Rendered printed str. 392 at 7× around that exact word:
   the book clearly prints **"IARU-a"** correctly. The "LARU" reading exists only in
   PyMuPDF's text layer (`get_text('words')` returns literally `'LARU-a'` at that
   position) — this is the identical failure mode that blocked P3-0012 a third time,
   caught here before it shipped. Rewrote the note and its citation to state plainly that
   the exam text is correct and the extraction is what misreads it.
2. **`bk-pra-3-17`** claimed the opposite kind of thing and — checked — was itself
   backwards: it attributed question 17's duplicate "c)" option label (four options, but
   the third and fourth are both printed "c)") to "OCR zbirke" (the collection's OCR).
   Rendered printed str. 390 at 8× around that line: the book's own typesetting genuinely
   prints "c)" twice — this is a real defect in the source, not an extraction artifact.
   Corrected the note's wording so it no longer blames OCR for something the book itself
   does.

Both fixes required rewriting the affected JSON spans in Python with explicit `chr()`
Unicode escapes rather than typing the characters directly — an intermediate tool pass was
silently converting straight ASCII quotes adjacent to the file's Croatian „...“ typographic
quotes into mismatched curly quotes, which twice broke JSON validity (caught immediately by
`json.load` failing, not by `rebuild.py`, which would have silently produced a truncated or
wrong parse). Confirmed byte-level afterward: zero stray U+201D characters remain, and the
file now parses cleanly.
