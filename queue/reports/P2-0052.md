# P2-0052 — Externalize quiz figures to images/ folder instead of base64-inlining

## Scope

Changed how the 135 figure PNGs reach `quiz.html`: previously `rebuild.py` base64-encoded each
one into `q["figure"]["data"]` as a `data:image/png;base64,...` URI, which `build_quiz.py`'s
`pack()` forwarded verbatim into the `f` field of every question in the packed `DATA` payload.
Now `rebuild.py` sets `q["figure"]["data"]` to a relative path (`images/<id>.png`) and copies the
135 source PNGs from `quiz/build/figs/` (HRS) and `quiz/build/figs_book/` (book) into a new
`quiz/images/` folder sitting next to `quiz.html`. `pack()` needed no functional change — it
already just forwards `figure.data` — so I only added a comment there and at the one runtime line
that sets `#qimg`'s `src` (`quiz/build/build_quiz.py` ~line 528 of the emitted HTML) explaining
why no code change was needed: `img.src` resolves a relative path against the page's own
location under both `file://` and `http(s)://`, unlike `fetch()`.

Also added a stale-file sweep (delete any `quiz/images/*.png` not currently referenced) so the
folder never drifts from `questions.json` across rebuilds, and added `quiz/images/` to
`.gitignore` next to the existing `quiz/questions.json`/`quiz/quiz.html` entries — same rationale
(regenerated deliverable, not something anyone edits, would conflict across branches) — and
updated that gitignore block's stale comment ("3.1 MB, base64 figures inline") to describe the
new layout. `.gitignore` isn't in the item's `files:` list; flagging that as a scope addition I
judged necessary to keep the new derived folder untracked, consistent with its two siblings.

`figure_is_options`/`fo` handling untouched, per Avoid. No gzip/chunk-loading attempted, per
Avoid.

## Unrelated finding, not fixed (out of scope)

Serving `quiz.html` over plain HTTP (no charset in the `Content-Type` header, e.g. Python's
`http.server`) renders Croatian diacritics as mojibake (e.g. "Izraäunaj" instead of "Izračunaj").
The generated HTML has no `<meta charset="utf-8">` tag and no `<!DOCTYPE html>` — under `file://`
the browser's charset sniffing happens to guess UTF-8 correctly, but a bare HTTP server without
an explicit charset does not. This is pre-existing in `build_quiz.py`'s `HTML` template (not
introduced by this item — I only added comments near the two lines this item touches) and is
unrelated to the figure path change: the figure itself rendered correctly over HTTP in the same
screenshot, only the surrounding text was garbled. Flagging per the brief's "found something else
worth doing — name it, leave it alone" rule; not fixed here.
