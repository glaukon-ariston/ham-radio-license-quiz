## A bug I found and fixed before it shipped

The existing global rule `@media(prefers-reduced-motion:reduce){*{animation:none!important}}`
does **not** stop animation on `::before`/`::after` pseudo-elements — a bare `*` never matches
them, they need to be named explicitly. This item is the first thing in the file to animate a
pseudo-element (`header.bar::after`'s new sweep, `.qcard::before`'s new breathing glow), so it's
the first thing that could expose this gap — and did: my first two "frozen" screenshots 2s apart
were *not* pixel-identical (header hairline still visibly sweeping) until I added explicit
`:root[data-theme="waterfall"] header.bar::after{animation:none}` and
`:root[data-theme="waterfall"] .qcard::before{animation:none;opacity:.18}` to the new
reduced-motion block. Re-tested after the fix: pixel-identical (sha1 match). Left the existing
global `*` rule untouched (rule outranking: don't edit shared rules) and patched the gap only
inside the new waterfall-scoped block, with a comment explaining why.

## Design note: why #fxbg's opacity lives on its children, not on `#fxbg` itself

The item's prose reads as if the ~.5-.6 opacity cap belongs on `#fxbg` itself. I put it on `.fx1`
and `.fx2` instead, with `#fxbg` keeping a **solid, opaque** `var(--fx-bg)` base. Reasoning: the
item also mandates `body{background:transparent}` so `#fxbg` (`z-index:-1`) can show through.
If `#fxbg`'s own CSS `opacity` were .55, that would fade its solid base too, exposing the
browser's default white canvas underneath at ~45% — a bad regression for a near-black theme,
and also breaks the reduced-motion "clean static look" requirement, since fully hiding `#fxbg`
under reduced motion would then blank the page to white instead of freezing on `var(--fx-bg)`.
Keeping `#fxbg` opaque and putting opacity only on the colourful overlay children avoids both
problems while still reading as "opacity around .5-.6" for the vivid content, which is what the
item is visibly asking for. Flagging this interpretation call explicitly since it diverges from
a literal reading of "opacity... on the layer itself" (that phrase is honored for the
hue-rotate `filter`, which *is* on `#fxbg` itself, as instructed).

## WCAG contrast check (item's step 3)

Wrote a one-off script (`contrast_p2_0062.py`, relative-luminance formula, standard "src over
dst" sRGB alpha compositing — not a library) modeling: each of the 5 `--fx-gradient` hues (at
the stop alpha `.fx1` actually uses) blended at the pessimistic worst end of the opacity cap
(.6) over `--fx-bg`, then `--card-glass` (card at 82%) composited over that, then `ink`/`muted`
checked against the result. Plus a 6th case, `--fx-bg` alone.

Worst case across all 6: **ink 15.90:1** (need ≥4.5), **muted 5.57:1** (need ≥3.0) — both
comfortably clear, no tuning needed, matching the item's own expectation ("this is a pessimistic
bound... it just means don't over-tune against it"). Full per-hue table is in the script's
output, reproducible by re-running it.

## Surprise not in scope — flagging, not fixing

The home screen's tables (`#secTable`/`#subTable`, `.note`, headings) sit directly on the body
background with no card wrapper — never in scope, since the item explicitly lists only five
selectors for `--card-glass` and says "don't widen." Before this item that background was
opaque `--paper`; now it's the animated layer. Same contrast model applied to bare text (no
card) against the worst hue gives **muted as low as 2.04:1** (below the 3:1 UI-component
threshold) and ink 5.81:1 (still fine) at the pessimistic .6 opacity end. This is a real, if
occasional (animation-phase-dependent, and the real `backdrop-filter`-free blend will vary),
legibility dip on the home screen's secondary (`--muted`) text — visible in my screenshot as
faint grey numbers over a bright yellow/green patch. Left alone per the item's explicit scope
and "Avoid" instruction; naming it here for a possible follow-up item.
