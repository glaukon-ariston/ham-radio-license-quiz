# P3-0006 — Book notes, skupina I tehnički (a)

## Scope

Wrote `quiz/build/notes_book_s1_tehnicki_a.json`: one teaching note per id in
`quiz/build/work/packet_book_s1_tehnicki_a.json` (30 ids, `bk-teh-1-01` through `bk-teh-1-59`,
odd numbers only — the `_a`/`_b` split interleaves on printed question number). Each note
follows the corpus's simple `{note, cite, formula?}` shape (no `notes_zzz_expanded_*` style
links section — `link_check.py` and `check_notes.py` only glob that prefix, so this file adds
no links at all rather than adding unverifiable ones).

## What was done

- Read the packet, then rendered/read the actual printed pages 288–297 of `Radiokomunikacije.pdf`
  with `booktool.py`/pymupdf for every one of the 30 questions — not just the OCR'd option
  text, the page images too, since several stems ("na slici", "prikazan je na slici") depend
  on a figure. Confirmed 6 of the 30 do carry a figure in the live build even though the
  packet's own `has_figure` field says `false` for all of them (that field is stale from
  before figures were restored by the P2-003x cluster): `bk-teh-1-05, -07, -09, -11, -19, -47`.
- Verified every citation against the book's own table of contents / section headings, not
  invented section numbers: e.g. `5.3.3. Odvojni stupanj` (str. 138) for the buffer question,
  `5.3.4. Pobudni stupanj` (str. 139) for the driver question, `9.1.1. O elektromagnetskoj
  kompatibilnosti` (str. 188) for the HI-FI demodulation question — each checked to actually
  contain matching prose, not just a plausible-sounding heading. Ran a script afterward that
  re-parses every `cite.loc` in the new file and confirms the printed page number really
  exists in `booktool.load('RK')`'s folio map — all pass.
- Worked the physics for every calculation question (harmonics, modulation depth, Kirchhoff's
  current law on the 5-current figure, F/B ratio in dB, inverse-square power density, T↔f) by
  hand and cross-checked the result is consistent with the packet's marked answer letter before
  writing the note — per rule 1, none of that changed anything; it was a check, not a rewrite.
- Rewrote the whole file once after noticing the first draft had silently dropped Croatian
  diacritics (wrote "služba" as "sluzba" throughout) — inconsistent with every other notes file
  in the corpus. Second draft uses proper č/ć/š/ž/đ.

## Two things found, not fixed

**1. `bk-teh-1-47`'s packet entry is stale, not currently wrong.** Cross-checking the packet
against a fresh `questions.json` (after running `rebuild.py`, required for verification anyway)
showed the packet's question/options for `bk-teh-1-47` — "koji filtar za VHF/TETRA/NMT/aviation
band" — do **not** match what the live build now serves. `book_overrides.json` already has a
`bk-teh-1-47` entry (added by **P2-0032**, see `queue/reports/P2-0032.md`) that patches this id
to its real content: a filter-response-curve picture question (`figure_is_options: true`,
options `a)`..`d)`), answer `b`. `book_figures.py` reapplies that patch to `book_parsed2.json`
on every `rebuild.py` run — confirmed live in this run's own output ("book stems patched from
overrides: [...'bk-teh-1-47'...]"). The **packet file was generated before that fix landed and
was never regenerated** (`make_packets.py` reads `questions.json`, not the override file
directly). I rendered the actual filter-curve image (pdf index 289, y 462–655) to see which of
the four curves is the flat-then-drops-at-30MHz low-pass shape, confirmed it matches "curve b)"
by inspection, and wrote the note around the *current, correct* question rather than the stale
packet text — this is a case of citing the live book_overrides.json/questions.json state, not
inventing anything. **Other still-open packets likely have the same staleness** for the rest of
that patched-id list: `bk-teh-1-04, bk-teh-1-06` (in packet `_b`, not this item),
`bk-teh-3-01/06/10/16/21/51/53`, `bk-teh-4-13/16/47`, `bk-teh-5-04/47/55`, `bk-teh-6-01/13/14`,
`bk-teh-5-60` — worth a queue item to regenerate all `packet_book_*.json` from current
`questions.json` before any more book-notes items are drained, so later workers don't repeat
this by-hand cross-check.

**2. `rebuild.py`'s note-attachment loop never sees book question notes at all.** Line 111:
`byid = {q["id"]: q for q in hrs}` — built only from the 456 HRS bank questions, never from
`extra` (the 720 book questions). The loop right after it does
`q = byid.get(qid); if not q: unknown.append(qid)` for every `notes_*.json` entry, so every one
of my 30 `bk-teh-1-*` notes currently prints as `! notes for unknown ids` and is silently
**not** attached to any question — confirmed in this run's own `rebuild.py` output. The build
still reports 1176 questions and passes integrity (this is not the kind of problem `rebuild.py`
aborts on — it has no way to know a book id "should" have a note), so nothing here fails this
item's own `Done when`, but it means the entire P3 book-notes cluster (this item and the ~20
after it) currently writes notes that don't reach the shipped quiz until `rebuild.py`'s `byid`
line is widened to `{q["id"]: q for q in hrs + extra}`. Flagging rather than fixing:
`rebuild.py` is not in this item's `files:`, and it is shared build infrastructure that every
other in-flight P3 item also depends on — a one-line fix, but it deserves its own item and a
regression check against the `explained_by_section` count in `_meta`, not a drive-by edit here.
