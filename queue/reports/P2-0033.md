## A systematic bug found in `fig_audit.py`'s proposer (not fixed — out of file scope)

The automated `[y0,y1]` proposals in `fig_windows.json` are **wrong, sometimes badly**,
whenever the real options are short (numbers, units, single words: "8000 Ω", "200 mA",
"SSB", "1kΩ"). `find_next_marker()`'s "real option" filter requires ≥6 normalised
characters; short numeric options fall under that bar, so the function misreads a normal
4-real-option question as a "hybrid" (some options are picture labels) and stops the
window at `last-real-option-bottom + 5` instead of `first-option-top - 1` — landing the
crop's bottom edge **inside or past the options themselves**. A second, separate bug: for
`bk-teh-2-12` (last question on its page, no next-question anchor), the proposer's
next-anchor scan latches onto the page's own **printed folio number** ("300" at the
bottom margin) as if it were a question-number anchor, producing a window that runs 67pt
past the real option block.

I did not trust any of `fig_windows.json`'s teh-2 proposals blindly — I re-derived every
window by hand from `book_parsed2.json`'s own already-correct option `y`-coordinates
(ground truth, not the heuristic) and cross-checked against the rendered page image.
Corrected vs. proposed, all in PDF points:

| id | proposed | used | why proposed was wrong |
|---|---|---|---|
| bk-teh-2-02 | [219, 385] | [219, 352] | short options ("8000 Ω" etc.) misread as hybrid |
| bk-teh-2-12 | [590, 784] | [590, 717] | folio "300" mistaken for a next-question anchor |
| bk-teh-2-15 | [287, 432] | [287, 397] | "SSB" (3 chars) misread as hybrid |
| bk-teh-2-16 | [477, 615] | [477, 569] | short options ("1kΩ" etc.) misread as hybrid |
| bk-teh-2-17 | [648, 767] | [648, 730] | short options (MHz values) misread as hybrid |
| bk-teh-2-19 | [187, 288] | [187, 288] | correct as proposed (all 4 options long text) |
| bk-teh-2-58 | [387, 529] | [387, 529] | correct as proposed (all 4 options long text) |

`bk-teh-2-04`/`06`/`08` (merged-block, no `y_hint` needed or supplied by hand) also came
out correct once I gave `find_stem` the right starting `y_hint` — without one, matching
"Sklop na slici je:" (which appears twice on page 294, for Q4 and Q6) from the top of the
page always lands on Q4's occurrence, so a naive call for Q6 would silently reuse Q4's
stem-end as Q6's — I did not use that path; I supplied `y_hint=380` by hand from the raw
page-line dump.

`fig_audit.py` is outside this item's `files:` list, so I did not patch the length
threshold or the folio-exclusion — but **0034–0037 should not trust `fig_windows.json`
values for any question with short/numeric options without the same by-hand check**,
and the same "identical stem text twice on one page" trap will recur for any other
shared-figure pair.
