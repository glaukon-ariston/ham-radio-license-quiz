# P1-0030 — Restore the missing sketch for bk-teh-5-60 and strip the answer from its stem

## Problem

`bk-teh-5-60` (RK, Ispitna pitanja SKUPINA V, pitanje 60, tiskana str. 343 = PDF page 338)
was already found by the coordinate parser (`num_source: "ocr anchor"`), so it never went
through `book_overrides.json`. Its stem ended `... Sigurnosna udaljenost iznosi 6,4m.
Potrebno je: 8m` — the trailing `8m` is the printed label on the left mast of the sketch
("8 m" in the drawing), which sits in the stem's x-column on the rendered page and got
stitched onto the stem text by `parse_book2.py`'s line-stitching logic (the same code path
that legitimately re-joins a wrapped stem line). Because `8m` matches key `b`
("umjesto desnog 4 m visokog stupa postaviti 8 m stup"), the stem was handing the answer
to anyone who read it.

## Why `book_overrides.json` alone could not fix it

`parse_book2.py`'s override-merge loop only *adds* questions the coordinate parser missed
entirely (`if qid in have: continue`). `bk-teh-5-60` parses fine except for the stem
bleed, so it is already in `have` and a normal override entry for it would be silently
ignored. Rather than touch `parse_book2.py` (outside this item's `files:` list), the fix
was added to `book_figures.py`, which already runs after `parse_book2.py` in the
`rebuild.py` pipeline and already reads `book_overrides.json`.

## What changed

**`quiz/build/book_overrides.json`**
- Added a new `_reasons` entry, `"figure-in-stem"`, describing this seventh case: the
  question parses correctly on its own, but a sketch between the stem and the options has
  its own printed label glued onto the stem.
- Added a `bk-teh-5-60` entry: `page: 338`, `figure: [481, 596]` (PDF points, measured off
  the rendered page — see below), and `question` with the `8m` tail stripped. `options` is
  the same dict the parser already found (unchanged), included only so the entry is
  self-contained and matches the shape of every other override.

**`quiz/build/book_figures.py`**
- Extended the module docstring to describe the new "figure-in-stem" case and why the fix
  lives here rather than in `parse_book2.py`.
- After the existing figure-cropping loop (unchanged), added a second pass: for every
  override with a `question` key, look up that id in the just-written
  `book_parsed2.json`. If found (i.e. the parser already parsed it independently) and the
  text differs, overwrite `question`/`options` in place and record `text_patched` (a new,
  otherwise-unused field — `rebuild.py` doesn't read it) with the reason. Deliberately
  does **not** touch `num_source`: `rebuild.py` string-matches `num_source == "ocr anchor"`
  exactly to decide whether the citation gets a "(broj pitanja rekonstruiran)" suffix, and
  the question *number* here was never in doubt — only the stem text was wrong. My first
  attempt appended to `num_source` and broke that check (the citation started claiming the
  number was reconstructed, which is false); caught it by diffing `questions.json` before
  and after, and reran the full pipeline after fixing it. Ids not already parsed are
  untouched by this new pass — `parse_book2.py`'s own loop still adds those exactly as
  before, so all 6 pre-existing override entries are unaffected (verified: rebuild still
  reports "book stems patched from overrides: ['bk-teh-5-60']", i.e. exactly one).

## Measuring the crop window (for 0031 to check against)

Rendered PDF page index 337 (page 338 = printed 343) at dpi 200 and inspected the text
block y-coordinates:
- stem block ends at `y1 = 480.8`
- the sketch's own "8m" label block sits at `y0=555.0 y1=565.0`
- option (a) starts at `y0 = 596.6`

So the figure occupies the gap between the stem and the first option. Window used:
**`[481, 596]`** (PDF points, `x` spans the full page width as in every other entry). Visual
check of the crop (`quiz/build/figs_book/bk-teh-5-60.png`, 813×240 after
`figures2.postprocess` trims/pads) confirms it shows exactly the two masts (8 m and 4 m),
the wire between them, and the house — no option text, no red marks (the sketch itself
contains no red in the source). There is a faint print-through ghost of the *next* page's
text visible at the very top of the crop; this is a pre-existing scan artifact of this PDF
(the same ghosting is visible in the already-shipped `bk-teh-5-52.png`), not something this
crop introduced, and it cannot be trimmed away without cutting into the roof of the sketch,
which starts almost immediately below the stem.
