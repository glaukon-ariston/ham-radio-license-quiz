# P1-0031 — Audit which book questions have a figure, and propose crop windows

## What was built

`quiz/build/fig_audit.py` — a new pipeline step (wired into `rebuild.py` right after
`book_figures.py`) that:

1. **Regression gate.** For every id `book_overrides.json` says has a `figure`, checks it
   is still present in `figs_book_index.json` (i.e. `book_figures.py` actually cropped it
   this run). If one has vanished, the script `sys.exit`s with the list of ids, which
   `rebuild.py`'s existing `run()` helper turns into a build abort. Confirmed working (all
   7 applied figures — the 6 pre-existing option-figure overrides plus `bk-teh-5-60` from
   item 0030 — pass on the current tree).
2. **Two independent detectors** over `book_parsed2.json`'s coordinate-parsed questions
   (i.e. everything the parser found real `y`/`opts` geometry for — this excludes the 6
   eye-transcribed `figure-options` overrides, which have no geometry to measure and are
   reported separately via the `figure` column):
   - **NAME**: the stem names a figure. Started from `figures2.py`'s own `FIGURE_WORD`
     regex (slika/slici/sliku/shem/crtež/dijagram/oscilogram/skic) and extended it with
     book-specific vocabulary the exam bank never needed — krivulja, graf, prikaz, zaslon,
     spektar, tlocrt, simbol — after checking by hand that questions like `bk-teh-4-17`
     ("Grafički simbol predstavlja:") and `bk-teh-3-21` ("Koja od krivulja predstavlja...")
     are genuinely about a picture. This catches **46** stems (the item's own count was 51;
     see "Numbers don't match the item's" below).
   - **GAP**: `min(option y) - stem y` in `book_parsed2.json` exceeds 60pt. This catches
     **64** — exactly the number the item cites, so I'm confident this detector matches
     whatever the item's author used. It is confirmed to catch `bk-teh-5-11` ("Koliki je
     napon U.?"), the item's own example of a figure with no naming word at all.
   - Union (either fires): **73** suspects. Both fire: **37**. Of the 73, only
     `bk-teh-5-60` already has a figure (the item 0030 pilot); **72 are outstanding**.
3. **Window proposer.** For every outstanding suspect, re-reads the actual PDF page with
   pymupdf (not the cached, sometimes-incomplete `book_parsed2.json` geometry) and:
   - Locates the stem's own last line by fuzzy-matching (`difflib`, not exact equality)
     the **already-correct** stem text against the page's raw OCR lines, so a line the OCR
     glued a stray figure-caption glyph onto (`bk-teh-2-20`'s "...napajanja? IH", the same
     bug item 0030 hand-fixed for `bk-teh-5-60`'s "...Potrebno je: 8m") doesn't throw off
     the boundary. A line whose own bbox is implausibly tall (>20pt — scanner noise, not
     real text height) is capped to a nominal 13pt line rather than trusted.
   - Locates where the figure ends using three rules chosen by how many of the four
     options are real text vs. a bare picture label ("a)"): all four real → stop at the
     top of the first option (normal case, e.g. `bk-teh-5-60`); some real → stop just
     below the last real one (`bk-teh-2-46`'s hybrid: three oscillogram thumbnails plus
     one textual "(d) ni jedan od prikazanih"); none real → stop just above the next
     question's own number anchor (pure picture-option questions); no anchor on the page
     at all → fall back to just above the printed folio (figure runs to the bottom of the
     page).
   - Writes `[y0, y1]` (rounded PDF points) to `fig_windows.json`, keyed by id. **Not
     applied anywhere** — nothing downstream reads this file; it exists purely for 0032-37
     to start from.

## Validation against ground truth (the item's explicit acceptance test)

Ran the proposer against all 7 windows that already exist by eye — the 6 in
`book_overrides.json` plus `bk-teh-5-60` (0030) — and printed the delta:

```
bk-teh-2-20    proposed [368, 578]   actual [360, 578]   delta  8.0pt  (next-anchor)
bk-teh-2-46    proposed [429, 562]   actual [418, 562]   delta 11.0pt  (option-bottom+5)  ** >10pt **
bk-teh-4-07    proposed [91, 242]    actual [96, 240]    delta  5.0pt  (next-anchor)
bk-teh-4-08    cross-reference -- shares bk-teh-4-07's figure, not a fresh proposal, skipped
bk-teh-4-36    proposed [92, 321]    actual [96, 318]    delta  4.0pt  (next-anchor)
bk-teh-5-52    proposed [535, 779]   actual [540, 760]   delta 19.0pt  (page-floor)  ** >10pt **
bk-teh-5-60    proposed [481, 596]   actual [481, 596]   delta  0.0pt  (option-top)
```

5 of 6 measurable windows are within the item's ~10pt usability bar (one exact). Two are
outside it, and I'm reporting both honestly rather than tuning the threshold to hide them
(the item explicitly warns against tuning to noise):

- **`bk-teh-2-46`, 11pt** — one point over. This is a hybrid case (3 picture options + 1
  text option) where the human-eyeballed window's top edge sits essentially at the very
  start of the stem's own last line rather than below it (the annotator was generous, not
  precise — `book_figures.py`'s `postprocess()` trims interior whitespace either way, so
  this looseness in the *ground truth itself* is plausibly why it doesn't sit inside 10pt
  of a principled rule). Borderline, not broken.
- **`bk-teh-5-52`, 19pt** — the "page-floor" fallback branch (no next-question anchor and
  no real option text on the page at all, because this is the last tehnicki question on
  its page). It overshoots toward the printed folio number rather than the true bottom of
  the figure's ink. The overshoot is in the *safe* direction (wider, not narrower — it
  cannot cut the figure off), and `postprocess()`'s own whitespace trim tightens most of
  the slack when the crop is actually taken. Still, this is the one branch of the three
  I'd flag for extra scrutiny in 0032-37: any row in `fig_windows.json` whose crop turns
  out to run to a page's bottom margin came from this fallback and deserves a second look.

Both are called out explicitly in `fig_audit.py`'s own printed calibration section (which
runs every time `rebuild.py` runs `fig_audit.py`), not just in this report.

## Numbers don't match the item's background count, and that's noted rather than forced

The item's text states 51/64/32 (name/gap/both). My gap count (64) matches exactly, which
gives confidence that detector is doing what whoever explored this first did. My name
count (46, even after extending the keyword list beyond `figures2.py`'s own) came up short
of 51 and I did not keep adding keywords to force the number to match — the item's own
"Avoid" is explicit that tuning to hit a number risks trading precision for false
positives ("a threshold tuned to noise costs trust in the audit"). The union is 73 rather
than 83. I'm flagging the gap rather than silently presenting 73 as if it were the
authoritative 83 — whichever extra ~10 stems used vocabulary I didn't think to add can be
picked up by hand in 0032-37 the same way `bk-teh-5-11` (no naming word at all) already is,
via the gap detector.
